# HONA Core 2.0 — инженерный контракт Claude Code

Каноническая архитектура: [`docs/architecture/HONA_CORE_2_ARCHITECTURE_V1_FINAL.md`](docs/architecture/HONA_CORE_2_ARCHITECTURE_V1_FINAL.md) — Architecture v1.0 Final, APPROVED 2026-09-23.
Этот файл — короткая выжимка обязательных правил. При любом расхождении прав архитектурный документ.

## Перед любой работой

1. Прочитать Architecture v1.0 Final: разделы, которые затрагивает задача, и §20 Final Architecture Check.
2. Не менять замороженную архитектуру молча. Любое отклонение — сначала отчёт владельцу и его решение, затем PR с новой версией документа.

## Данные

3. PostgreSQL — source of truth.
4. В HONA Core 2.0 нет whole-board JSON state: одна сущность — одна таблица (§5).
5. JSONB допустим только для обоснованных metadata, settings и config; перечень мест — §20.1, пункт 1.
6. Изоляция компаний обеспечивается и backend, и базой: `ctx.companyId` в каждом запросе репозитория, `404` для чужих и невидимых сущностей, составные tenant-FK в PostgreSQL (§5.1, §8.4, §8.5).
7. Никакого `ON DELETE CASCADE`: политика FK — `NO ACTION`, архив вместо удаления (§21).
8. Миграции только forward-only; применённый файл миграции не редактируется (§16).
9. Файлы не хранятся base64-payload в PostgreSQL или JSON. Байты лежат в S3/MinIO (приватный bucket, presigned-ссылки только после авторизации), в PostgreSQL — только метаданные (§12).

## Домен

10. Project ≠ Board.
11. Column ≠ Workflow Status.
12. Task может существовать без размещения на Board (§6.1).
13. Статус задачи меняется только через workflow engine и `POST /tasks/:id/transition`. Прямое произвольное изменение статуса запрещено (§7).
14. Optimistic concurrency обязательна для изменяемых сущностей: `version` + `If-Match`, при конфликте `409` (§6.5).
15. `Idempotency-Key` обязателен для команд создания (§9.1).
16. Domain events + transactional outbox — архитектурный фундамент: событие пишется в той же транзакции, что и данные; побочные эффекты — только из outbox (§10).

## Безопасность

17. RBAC проверяется только server-side. Права во frontend — это UX, а не граница безопасности (§8).
18. AI никогда не обходит RBAC: он действует от имени пользователя и через те же сервисы (§22.1).
19. Разрушающие и любые записывающие действия AI выполняются только после подтверждения человеком (§22.1).
20. HONA ORDER, Stock, Attendance и AVR не получают прямого доступа к БД HONA Core: только API, события и версионированные контракты (§22.2).
21. Секреты только в окружении. `.env` не коммитится; IP серверов, ключи и пароли в репозиторий не попадают.

## Git и процесс

22. `main` — стабильный замороженный v1. Прямых коммитов в `main` нет.
23. `v1-final` — неизменяемая легаси-точка отсчёта: не перемещать и не удалять.
24. Разработка 2.0 идёт через `develop-2.0`, ветки фаз и PR. Merge делает владелец.
25. Никакого force push в защищённые ветки и никакого переписывания истории.
26. Код 2.0 живёт только в `hona-core/`. Легаси в корне репозитория не меняется и не импортируется.
27. Фазы идут по плану §18: блок STATUS перед фазой, блок RESULT после неё.
28. Нельзя автоматически переходить к следующей Phase. После каждой фазы — отчёт и STOP до разрешения владельца.
