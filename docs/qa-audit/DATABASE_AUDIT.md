# Аудит базы данных

СУБД: PostgreSQL 16. ORM не используется — SQL пишется напрямую в
`api/server.js`. Схема создаётся идемпотентно при старте API (`ensureSchema()`),
отдельной системы миграций нет.

**Важно:** к боевой базе обращений не производилось. Данные не читались, не
изменялись и не удалялись; `DROP`/`TRUNCATE` не выполнялись. Схема проверена по
коду, целостность — по логике приложения и тестами.

## Таблицы

| Таблица | Назначение | Ключи и индексы |
|---|---|---|
| `board_state` | всё состояние доски одной строкой JSONB (`id='default'`) | PK `id` |
| `users` | сотрудники | PK `id`, UNIQUE `login` |
| `sessions` | сессии входа | PK `token`, колонка `user_id` |
| `notif_log` | защита от повторной отправки уведомлений | PK `key` |
| `board_history` | снимки доски перед перезаписью (добавлено аудитом) | PK `id`, индекс `(board_id, created_at DESC)` |

## Замечания к схеме

### 1. Реляционной модели задач нет (принципиальная особенность)
Проекты, списки, карточки, комментарии, чек-листы и вложения **не являются
таблицами** — всё это ключи внутри одного JSONB-документа. Следствия:

- внешние ключи, каскадное удаление и ограничения целостности на уровне базы
  неприменимы: целостность обеспечивает только фронтенд;
- запросы вида «все задачи сотрудника» на стороне базы невозможны — нужно читать
  и разбирать весь документ;
- нет полей `createdBy` / `updatedBy` у задач, нет журнала изменений;
- нет истории и мягкого удаления (soft delete): удалённая карточка исчезает из
  документа безвозвратно (частично компенсировано снимками `board_history`).

Пункты задания про внешние ключи, каскады и связи проверить нельзя — этих
сущностей в базе нет. Переход на реляционную модель — та же задача, что и
пооперационный API (`BUGS_REMAINING.md`, R-01).

### 2. Целостность внутри документа
Проверено логикой приложения и тестами:

| Проверка | Результат |
|---|---|
| Карточки без существующего списка | не возникают: удаление списка удаляет его карточки |
| Ссылки на несуществующие карточки в `cardIds` | отсеиваются при отрисовке (`.filter(Boolean)`) |
| Дублирующиеся исполнители | невозможны: переключение проверяет наличие |
| Одинаковые коды задач | **были возможны**, устранено (B-03), покрыто тестом |
| Прогресс выше 100% или отрицательный | невозможен: считается из фактических пунктов |
| Ссылки на удалённых пользователей | обрабатываются: отсутствующий пользователь отфильтровывается |
| Некорректный корневой документ | **был возможен**, устранён проверкой на сервере (B-01) |

### 3. Отсутствует очистка просроченных сессий
Сессии проверяются по возрасту (`created_at > now() - 30 days`), но старые строки
никогда не удаляются. На скорость это не влияет (обращение по первичному ключу),
но таблица растёт бесконечно.

**Рекомендация:** удалять просроченные при старте API:
```sql
DELETE FROM sessions WHERE created_at < now() - interval '30 days';
```

### 4. Нет системы миграций
Схема правится вызовами `CREATE TABLE IF NOT EXISTS` и
`ALTER TABLE ADD COLUMN IF NOT EXISTS`. Для текущего масштаба это работает и
безопасно (операции идемпотентны, данные не теряются), но не даёт ни версий
схемы, ни отката.

**Рекомендация:** при переходе на реляционную модель ввести миграции
(например, `node-pg-migrate`).

### 5. Резервное копирование
В репозитории есть `deploy/backup.sh`, но расписание не настроено.
Снимки `board_history` — страховка от ошибочной перезаписи, а **не** замена
резервным копиям: они хранятся в той же базе.

**Рекомендация (важно):** настроить `pg_dump` по расписанию с выгрузкой за
пределы сервера и **проверить восстановление** на тестовом стенде.

## Итог

Схема соответствует текущему масштабу, но не даёт гарантий целостности на уровне
базы — их обеспечивает приложение. Критичная брешь (запись некорректного
документа) закрыта. Основные рекомендации: настроить резервное копирование по
расписанию, добавить очистку сессий, а при росте — переходить на реляционную
модель задач.
