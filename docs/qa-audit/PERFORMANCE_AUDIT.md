# Аудит производительности

Измерения выполнены на production-сборке. Нагрузочное тестирование боевого
сервера не проводилось.

## Размер сборки

| Файл | Размер | В сжатом виде (gzip) |
|---|---|---|
| `index-*.js` | 410 КБ | ~120 КБ |
| `index-*.css` | 34 КБ | ~7 КБ |
| Всего `dist` | 528 КБ | — |

Оценка: для внутренней системы это нормально. Весь JS — один файл: разделения
на части (code splitting) нет, но при таком размере выигрыш был бы небольшим.
Ассеты содержат хеш в имени и кэшируются nginx на год; `index.html` не
кэшируется, поэтому обновления подхватываются сразу. Сервис-воркер (PWA)
кэширует 15 файлов и отдаёт приложение мгновенно при повторных заходах.

## Найденные узкие места

### 1. Пересчёт всей доски при каждом изменении (средний приоритет)
`deriveView()` в `src/store/boardStore.tsx` перестраивает представление активной
доски при любом изменении состояния, а `Dashboard` пересчитывает все показатели
при каждом обновлении стора. На текущих объёмах (десятки–сотни задач) это
незаметно. При нескольких тысячах карточек появятся задержки ввода.

**Рекомендация:** при росте объёмов — мемоизация по спискам и виртуализация.

### 2. Нет виртуализации длинных списков (низкий приоритет)
Колонка доски и таблица отрисовывают все карточки сразу. Для 1000+ задач в одном
списке это даст заметное замедление прокрутки. Проверить это в среде аудита не
удалось: реальной базы нет, а генерация такого объёма в браузере не отражала бы
поведение с сервером.

**Рекомендация:** измерить на боевых объёмах; при необходимости — виртуализация
таблицы и колонок.

### 3. Полная передача доски при каждом сохранении (высокий приоритет)
Каждое изменение через 700 мс отправляет на сервер **всё** состояние доски.
При 1000 задач это сотни килобайт на каждое нажатие клавиши в описании.
Это же является причиной потери правок при совместной работе
(`BUGS_REMAINING.md`, R-01).

**Рекомендация:** пооперационный API — решает и производительность, и конфликты.

### 4. Один таймер на экран (сделано хорошо)
Обратный отсчёт до дедлайна на всех карточках обновляется одним общим
интервалом в 30 секунд (`src/store/now.tsx`), а не таймером на каждой карточке.
Это правильное решение, менять не нужно.

### 5. Снимки истории (добавлено аудитом)
Снимок предыдущего состояния пишется не чаще раза в 5 минут (и обязательно при
резком уменьшении числа карточек), хранятся последние 50. Рост базы ограничен;
на частоту автосохранений влияния нет.

## Запросы к базе

Запросов немного, N+1 отсутствует: доска читается одной строкой, список
пользователей — одним запросом. Индексы: первичные ключи + уникальный `login` +
добавленный индекс по `board_history`. Отдельный индекс для `sessions.token` не
нужен — это первичный ключ.

**Замечание:** таблица `sessions` не очищается от просроченных записей. За год
работы накопятся тысячи строк — на скорость не повлияет, но стоит добавить
периодическую очистку (см. `DATABASE_AUDIT.md`).

## Итог

Для 17–20 сотрудников текущая производительность достаточна. Главный риск при
росте — не скорость интерфейса, а объём передаваемых данных при сохранении
(пункт 3). Оптимизировать что-либо ещё до появления реальных объёмов
преждевременно.
