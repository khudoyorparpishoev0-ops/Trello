# QA-аудит платформы CORE (IT-HONA)

Дата аудита: 2026-08-06 · Ветка: `claude/kanban-platform-prototype-0y8wef`

Аудит выполнен по коду репозитория и на собранной production-версии приложения.
К боевой базе данных на сервере обращений **не производилось**: реальные данные
не читались, не изменялись и не удалялись.

### Формы, валидация, роутинг — фактическое положение

- **Библиотеки форм и валидации не используются.** Формы — контролируемые
  React-поля, проверки написаны вручную на фронтенде и (отдельно) на сервере.
- **Роутера нет.** Экран выбирается состоянием `view` в `src/App.tsx`.
  Прямые ссылки на разделы, история браузера и кнопки «назад/вперёд» не работают —
  см. `BUGS_REMAINING.md`, пункт R-04.
- **Realtime отсутствует.** WebSocket не используется, обновление у второго
  пользователя происходит только при перезагрузке страницы.

## 2. Карта архитектуры

```
Браузер (SPA, PWA)
  └─ Caddy :80/:443 ──┬─ /api/*  → api:3000 (Node http)
                      └─ /*      → frontend:80 (nginx, статика Vite)

api:3000
  ├─ PostgreSQL: board_state (вся доска одним JSON), users, sessions,
  │              notif_log, board_history (добавлена аудитом)
  ├─ Redis   : только health-check
  ├─ MinIO   : не подключён
  └─ Telegram: long-polling, уведомления о назначении/смене срока/дедлайнах
```

**Ключевая архитектурная особенность.** Всё состояние доски (проекты, списки,
карточки, комментарии, чек-листы) хранится **одной строкой** `board_state.id='default'`
в виде JSON. Фронтенд загружает блоб целиком (`GET /api/board`) и целиком же
перезаписывает (`PUT /api/board`) с задержкой 700 мс после изменения.
Из этого следуют два свойства, определившие большинство находок аудита:

1. любой некорректный `PUT` затирал данные всей компании (исправлено, см. B-01);
2. одновременная работа двух пользователей приводит к потере правок —
   побеждает последняя запись (не исправлено, см. `BUGS_REMAINING.md`, R-01).

### Аутентификация и роли — фактическое положение

Режим определяется переменными окружения:

| Условие | Режим |
|---|---|
| задан `INVITE_CODE` | личные аккаунты (регистрация по коду) |
| иначе задан `AUTH_PASSWORD` | общий вход (один логин на всех) |
| иначе | доступ открыт без входа |

Сессия — cookie `sid` (HttpOnly, SameSite=Lax, 30 дней), таблица `sessions`.
Пароли — scrypt с индивидуальной солью.

**Ролей в системе фактически две:** `admin` (первый зарегистрировавшийся) и
`member`. Единственное различие в правах — сброс чужого пароля
(`POST /api/users/reset-password`, только admin). Ролевой модели уровня
«владелец / руководитель отдела / наблюдатель / приглашённый», многокомпанийности
(multi-tenant) и приватных проектов в коде **нет** — это не дефекты, а
нереализованная функциональность. Подробнее — раздел 5 и `BUGS_REMAINING.md`.

## 3. Команды запуска

Раньше в проекте не было ни одной команды для тестов. Добавлены:

| Задача | Команда |
|---|---|
| Разработка (frontend) | `npm run dev` |
| Production-сборка | `npm run build` |
| Просмотр сборки | `npm run preview` |
| Проверка типов | `npm run typecheck` |
| Линтер | `npm run lint` |
| Unit-тесты | `npm run test:unit` |
| Тесты серверных защит | `npm run test:api` |
| Unit + API | `npm test` |
| E2E (Playwright) | `npm run test:e2e` |
| **Всё сразу перед релизом** | `npm run verify` |
| Полный стек (БД, API, фронтенд) | `docker compose up -d --build` |
| Только фронтенд | `docker compose up -d --build frontend` |
| Миграции | отдельной команды нет: схема создаётся идемпотентно в `ensureSchema()` при старте API |

Тесты работают **без новых зависимостей**: раннер — встроенный `node:test`,
типы снимаются флагом `--experimental-strip-types` (Node ≥ 22.6).
Playwright берётся из `node_modules`, если установлен, иначе из системной
установки (`PLAYWRIGHT_PATH`).

## 5. Чего в системе нет (не дефекты, а отсутствующая функциональность)

Значительная часть пунктов исходного задания описывает возможности, которые в
платформе не реализованы. Тестировать их невозможно; они вынесены в
`BUGS_REMAINING.md` как задачи развития:

- многокомпанийность (multi-tenant) и изоляция данных между компаниями;
- рабочие пространства как отдельная сущность с правами;
- расширенная ролевая модель, приглашения, деактивация и блокировка сотрудников;
- приватные проекты и разграничение видимости задач;
- вложения (MinIO поднят, но загрузка файлов не реализована);
- учёт времени и таймеры (стикеры показывают статичные значения);
- повторяющиеся задачи (стикер «каждую неделю» — только метка, планировщика нет);
- уведомления в интерфейсе (есть только Telegram);
- realtime и совместная работа;
- восстановление пароля по e-mail (SMTP не настроен);
- история изменений задачи, архив задач как отдельная сущность;
- экспорт данных, аналитика по периодам.

## 7. Итоговый статус

### RELEASE READY WITH WARNINGS

Публиковать можно. Критическая проблема потери данных устранена и покрыта
тестами, production-сборка проходит, регрессия зелёная.

Условия, которые нужно принять осознанно:

1. **Одновременное редактирование теряет правки** (R-01, P1). Архитектура
   «вся доска одним блобом» не поддерживает слияние. Риск снижен снимками
   истории (данные восстановимы), но не устранён. Для 17–20 человек, работающих
   в одной доске одновременно, это будет проявляться. Требует перехода на
   пооперационный API — работа на несколько дней, вне рамок аудита.
2. **Ролевая модель минимальна.** Любой вошедший сотрудник может изменить и
   удалить любую задачу и любой проект. Если это неприемлемо — нужна разработка
   прав доступа (R-02).
3. **Firefox и Safari не проверены** — в среде аудита нет этих браузеров.
   Перед широким запуском проверьте вручную или установите браузеры Playwright.

Подробности — в остальных файлах каталога `docs/qa-audit/`.
