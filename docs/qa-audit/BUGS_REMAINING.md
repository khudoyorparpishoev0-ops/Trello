# Нерешённые вопросы и задачи развития

Здесь то, что **нельзя было безопасно исправить автоматически**: изменения
затронули бы архитектуру или поведение, которое должен утвердить владелец
продукта. Для каждого пункта описаны риск и предлагаемое решение.

---

## R-01 · P2 · Одновременное редактирование: правки больше не теряются молча

> Было P1. Шаг 1 рекомендации выполнен: молчаливая потеря данных устранена,
> осталось целевое решение — пооперационный API.

**Суть (как было).** Вся доска хранится одним JSON-блобом и перезаписывается
целиком. Клиент сохраняет состояние через 700 мс после любого изменения. Если
два сотрудника работали одновременно, сохранение второго затирало правки
первого — молча, без предупреждения.

**Что сделано.** Версионирование записи:

- у `board_state` появился столбец `version`, растущий на каждой записи;
- `GET /api/board` отдаёт номер заголовком `X-Board-Version` (тело осталось
  прежним — состоянием доски, чтобы не ломать уже работающие клиенты);
- `PUT /api/board` принимает тот же заголовок и при расхождении отвечает `409`
  **не записывая ничего**; условие по версии стоит в самом `UPDATE`, поэтому
  запрос, вклинившийся между чтением и записью, тоже не проходит;
- клиент останавливает автосохранение и показывает плашку. Набранный текст с
  экрана **не откатывается** — человек выбирает: «Обновить» (взять версию
  сервера) или «Записать мою версию» (перезаписать чужую осознанно).

Клиент без заголовка версии пишет как раньше: так ведёт себя фронтенд,
выкачанный в кеш браузера до обновления, и отклонять его значило бы сломать
работу людям в момент выкладки.

**Что осталось.** Ситуация из «данные теряются молча» стала «одна из двух
версий теряется по решению человека». Слияние правок по полям это не даёт:
двое, редактировавшие разные карточки, всё равно выбирают одну версию целиком.

**Проверено.** `tests/api/guards.test.ts` — решение о конфликте;
`tests/db/version.test.mjs` — SQL, рост версии и гонка двух одновременных
записей на настоящем PostgreSQL; `tests/e2e/run.mjs`, раздел «Конфликт
версий» — обе кнопки плашки.

**Страховка сохраняется.** Снимки истории (`board_history`, последние 50,
обязательный снимок при потере более 20% карточек) — см. `TESTING_GUIDE.md`.

**Рекомендация.** Целевое решение прежнее: пооперационный API
(создание/изменение/перемещение отдельной карточки) + WebSocket для
синхронизации. Тогда двое смогут править разные карточки без выбора версии.

**Кто должен решить.** Владелец продукта — когда браться за пооперационный API.

## R-02 · P2 · Ролевая модель минимальна: удаление проектов закрыто, остальное — нет

> Было P1. Выполнена быстрая мера из рекомендации: удаление проекта — только
> администратору, проверка на сервере. Матрица прав на остальные операции
> по-прежнему за владельцем продукта.

**Суть.** В системе две роли: `admin` (первый зарегистрировавшийся) и `member`.
Эндпоинт `PUT /api/board` принимает состояние целиком, поэтому разграничение
прав возможно только сравнением прежнего состояния с новым.

**Что сделано.** Самая дорогая операция закрыта: удаление проекта уносит все
его задачи, а восстановить их можно лишь из снимков истории.

- Сервер сравнивает списки досок до и после записи. Если доска исчезла, а
  участник не администратор — `403 forbidden_board_delete`, **ничего не
  записывается**, в ответе названы затронутые проекты.
- Архивация под ограничение не попадает: доска остаётся в состоянии с флагом
  `archived`. Участнику по-прежнему доступны все остальные правки.
- Режим открытого доступа (вход выключен) работает как раньше: ролей в системе
  нет вообще, ограничивать нечем. При общем пароле сессия считается
  администраторской — это тоже прежнее поведение.
- В интерфейсе пункт «Удалить» не прячется, а гаснет с причиной и подсказкой
  про архив: исчезнувшая команда выглядит сбоем, а не ограничением прав.
- Если отказ всё же пришёл (интерфейс устарел), клиент забирает состояние с
  сервера и объясняет причину плашкой. Иначе удалённый проект пропал бы с
  экрана, оставшись живым в базе.

**Что осталось.** Всё прочее — создание и изменение задач, списков, состав
участников, удаление списков и карточек — доступно любому вошедшему. Это
осознанный остаток: матрицу прав должен утвердить владелец продукта, а
разграничение по отдельным операциям упирается в архитектуру «одного блоба».

**Проверено.** `tests/api/guards.test.ts` — правило (архивация не удаление,
роли, открытый режим); `tests/db/board.test.mjs` — отказ участнику, разрешение
администратору и то, что участник по-прежнему может править и архивировать;
`tests/e2e/run.mjs`, раздел «Отказ по правам» — объяснение в интерфейсе.

**Рекомендация.** Определить матрицу прав целиком и реализовать вместе с
пооперационным API (см. R-01).

**Кто должен решить.** Владелец продукта — состав ролей и что кому доступно.

## R-03 · P2 · Данные сотрудников доступны любому вошедшему

**Суть.** `GET /api/users` отдаёт всем авторизованным пользователям полный
список сотрудников с e-mail, датой рождения, должностью и отделом.

**Оценка.** Для внутренней системы компании на 20 человек это, скорее всего,
приемлемо: те же данные показываются в разделах «Команда» и «Компания».
Помечено как замечание, а не дефект.

**Рекомендация.** Если политика компании требует ограничений — отдавать
контактные данные только администраторам, остальным лишь имя, фото и отдел.

## R-04 · Закрыт · Адресация разделов

**Было.** Роутер отсутствовал, экран хранился в состоянии React. Нельзя было
дать коллеге ссылку на задачу или раздел; кнопки «назад» и «вперёд» выходили из
приложения; после перезагрузки открывалась доска, а не тот раздел, где работал
пользователь. Единственным исключением была ссылка `/?board=<id>`.

**Что сделано.** Адресация на History API, без сторонней библиотеки:

```
/dashboard · /team · /calendar · /company · /reports · /settings
/board/<boardId>            — канбан
/board/<boardId>/timeline   — таймлайн
/board/<boardId>/table      — таблица
?card=<cardId>              — панель задачи поверх любого раздела
```

`react-router` не добавлялся намеренно: семь экранов и два параметра не окупают
новую зависимость и перестройку навигации во всех разделах. Разбор и сборка
адреса — чистые функции в `src/lib/route.ts`, состояние и History API — в
`src/store/router.tsx`.

Решения, которые стоит знать:

- **Карточка — параметр запроса, а не сегмент пути.** Панель задачи открывается
  и с дашборда, и из календаря, и из отчётов, где сегмента доски в адресе нет.
  Ссылка на задачу с другой доски сама открывает нужную доску.
- **Прежние ссылки `/?board=<id>` работают** и приводятся к новому адресу: их
  уже разослали кнопкой «Скопировать ссылку». Сама кнопка теперь копирует
  новый формат.
- **Неизвестный путь открывает доску.** Страницы «404» в системе нет, и
  придумывать её ради опечатки в адресе незачем.
- **Выбранный вид доски сохраняется** при уходе в другой раздел и возврате:
  человек вернулся в раздел, а не сбросил свою настройку.
- **Фильтры в адрес не пишутся** — это состояние работы, а не место, куда дают
  ссылку. Вкладка «Задачи» на телефоне по-прежнему включает «Мои карточки».

**Побочно закрыто.** Открытая доска (`activeBoardId`) хранится в общем
документе, то есть переключение раздела у одного человека было записью, видимой
всем. С адресацией такие переключения стали частыми, а с версионированием
(R-01) каждая запись поднимала версию и роняла чужие сохранения в конфликт.
Теперь состояние, отличающееся только открытой доской, на сервер не пишется:
она у каждого своя и живёт в адресе.

**Проверено.** `tests/unit/route.test.ts` — разбор и сборка адресов, включая
прежний формат и экранирование; `tests/e2e/run.mjs`, раздел «Адресация» —
переходы, «назад» и «вперёд», перезагрузка, прямая ссылка на раздел, вид доски
в адресе, ссылка на задачу и совместимость со старым форматом.

**Осталось.** Раздача статики уже настроена под SPA (`try_files` в
`deploy/nginx.conf`, `navigateFallback` у service worker), отдельных действий
при выкладке не требуется.

## R-05 · P3 · Смешение языков в интерфейсе

**Суть.** Интерфейс русский, но демонстрационные списки называются «To Do»,
«In Progress», «Done». Системы локализации (i18n) нет — строки заданы прямо в
коде.

**Почему не исправлено.** Переименование затронуло бы уже существующие данные на
боевом сервере (пользователи создали свои списки), а внедрение i18n — это
отдельная задача. Хаотичная замена строк запрещена условиями аудита.

**Рекомендация.** Переименовать демо-списки при следующем создании доски и
внедрить i18n, если планируется таджикская версия.

## Отсутствующая функциональность (не дефекты)

Пункты задания, описывающие возможности, которых в системе нет. Тестировать
нечего; перечислены как задачи развития.

| Возможность | Состояние |
|---|---|
| Многокомпанийность, изоляция данных между компаниями | не реализовано (система однокомпанийная) |
| Рабочие пространства с правами | не реализовано (есть одно, декоративное) |
| Приватные проекты, разграничение видимости | не реализовано |
| Приглашения, деактивация, блокировка сотрудников | не реализовано (регистрация свободная — по коду из письма на корпоративный домен) |
| Изменение роли пользователя | не реализовано (роль выдаётся при регистрации) |
| Вложения к задачам | MinIO поднят, загрузка не реализована; в интерфейсе — только демо-данные |
| Учёт времени, таймеры | стикеры показывают статичные значения, счёта нет |
| Повторяющиеся задачи | стикер «каждую неделю» — метка, планировщика нет |
| Уведомления в интерфейсе, счётчик непрочитанных | не реализовано (есть только Telegram) |
| Realtime, совместное присутствие | не реализовано |
| Восстановление пароля по e-mail | не реализовано; после настройки SMTP препятствий нет — механика кода из письма уже есть |
| История изменений задачи | не реализовано |
| Экспорт данных, аналитика по периодам | не реализовано |
| Архив задач как отдельная сущность | не реализовано (используется обычный список) |
| CI/CD | не настроен |

## Что нужно от владельца для завершения аудита

1. Доступ к тестовому стенду с копией боевой базы — часть проверок (объёмы
   данных, миграции, поведение под нагрузкой) невозможно выполнить без боевых
   данных. Записи доски это уже не касается: `npm run test:db` поднимает API на
   настоящем PostgreSQL и проверяет версии, гонку и права.
2. Браузеры Firefox и WebKit для кросс-браузерной проверки
   (`npx playwright install firefox webkit`).
3. Решение по остаткам R-01 и R-02 — продуктовые вопросы, а не технические:
   когда браться за пооперационный API и какой должна быть матрица прав.
