# Нерешённые вопросы и задачи развития

Здесь то, что **нельзя было безопасно исправить автоматически**: изменения
затронули бы архитектуру или поведение, которое должен утвердить владелец
продукта. Для каждого пункта описаны риск и предлагаемое решение.

---

## R-01 · P1 · Одновременное редактирование теряет правки

**Суть.** Вся доска хранится одним JSON-блобом и перезаписывается целиком.
Клиент сохраняет состояние через 700 мс после любого изменения. Если два
сотрудника работают одновременно, сохранение второго затирает правки первого —
молча, без предупреждения.

**Как воспроизвести.** Открыть доску в двух браузерах. В первом переименовать
задачу, во втором — переместить другую карточку. Сохранения перекроют друг друга;
одна из правок исчезнет после перезагрузки.

**Почему не исправлено автоматически.** Корректное решение — перевод API на
пооперационные запросы (создание/изменение/перемещение отдельной карточки)
и разрешение конфликтов на уровне полей. Это переработка и сервера, и стора —
несколько дней работы с риском задеть всё приложение.半-мера в виде проверки
версии с ответом `409` в текущем интерфейсе означала бы, что у пользователя
внезапно откатывается набранный текст: для системы, которой уже пользуются,
это хуже текущего поведения.

**Что сделано для снижения риска.** Добавлены снимки истории (`board_history`,
последние 50, обязательный снимок при потере более 20% карточек). Данные,
затёртые в результате гонки, можно восстановить (см. `TESTING_GUIDE.md`).

**Рекомендация.**
1. Ближайший шаг (1–2 дня): добавить в `board_state` номер версии, возвращать
   его в `GET`, требовать в `PUT`, при расхождении отвечать `409`; на клиенте —
   не откатывать ввод, а показывать плашку «доска изменена, обновить».
2. Целевое решение: пооперационный API + WebSocket для синхронизации.

**Кто должен решить.** Владелец продукта — приемлемо ли текущее поведение до
перехода на пооперационный API.

## R-02 · P1 · Ролевая модель минимальна: любой сотрудник может удалить любой проект

**Суть.** В системе две роли: `admin` (первый зарегистрировавшийся) и `member`.
Единственное различие — сброс чужого пароля. Всё остальное — создание,
изменение, удаление задач, списков и проектов, изменение состава участников —
доступно любому вошедшему сотруднику. Ограничений на уровне API нет: эндпоинт
`PUT /api/board` принимает состояние целиком.

**Риск.** Сотрудник может (в том числе случайно) удалить чужой проект вместе с
задачами. Восстановление возможно только из снимков истории.

**Почему не исправлено автоматически.** Требуется решение владельца: какие роли
нужны, кто что может, как быть с уже созданными данными. Технически это влечёт
разграничение прав на уровне отдельных операций, что упирается в ту же
архитектуру «одного блоба» (R-01).

**Рекомендация.** Определить матрицу прав, реализовать вместе с пооперационным
API. Как быстрая мера — ограничить удаление проектов ролью `admin`
(проверка на сервере, не только в интерфейсе).

## R-03 · P2 · Данные сотрудников доступны любому вошедшему

**Суть.** `GET /api/users` отдаёт всем авторизованным пользователям полный
список сотрудников с e-mail, датой рождения, должностью и отделом.

**Оценка.** Для внутренней системы компании на 20 человек это, скорее всего,
приемлемо: те же данные показываются в разделах «Команда» и «Компания».
Помечено как замечание, а не дефект.

**Рекомендация.** Если политика компании требует ограничений — отдавать
контактные данные только администраторам, остальным лишь имя, фото и отдел.

## R-04 · P3 · Нет адресации разделов: не работают ссылки и кнопка «назад»

**Суть.** Роутер отсутствует, экран хранится в состоянии React. Следствия:
нельзя дать коллеге ссылку на конкретную задачу или раздел; кнопки «назад» и
«вперёд» в браузере выходят из приложения; после перезагрузки открывается доска,
а не тот раздел, где работал пользователь. Единственное исключение — ссылка на
доску вида `/?board=<id>`.

**Почему не исправлено.** Добавление роутера (например, `react-router`) — это
новая зависимость и перестройка навигации во всех разделах, включая мобильное
меню. Изменение заметное для пользователей, требует согласования.

**Рекомендация.** Внедрить роутер и адреса вида `/board/:boardId/card/:cardId`.

## R-05 · P3 · Смешение языков в интерфейсе

**Суть.** Интерфейс русский, но демонстрационные списки называются «To Do»,
«In Progress», «Done». Системы локализации (i18n) нет — строки заданы прямо в
коде.

**Почему не исправлено.** Переименование затронуло бы уже существующие данные на
боевом сервере (пользователи создали свои списки), а внедрение i18n — это
отдельная задача. Хаотичная замена строк запрещена условиями аудита.

**Рекомендация.** Переименовать демо-списки при следующем создании доски и
внедрить i18n, если планируется таджикская версия.

## Отсутствующая функциональность (не дефекты)

Пункты задания, описывающие возможности, которых в системе нет. Тестировать
нечего; перечислены как задачи развития.

| Возможность | Состояние |
|---|---|
| Многокомпанийность, изоляция данных между компаниями | не реализовано (система однокомпанийная) |
| Рабочие пространства с правами | не реализовано (есть одно, декоративное) |
| Приватные проекты, разграничение видимости | не реализовано |

| CI/CD | не настроен |

## Что нужно от владельца для завершения аудита

1. Доступ к тестовому стенду с копией боевой базы — часть проверок (реальные
   роли, объёмы данных, миграции, поведение под нагрузкой) невозможно выполнить
   без работающей базы. В среде аудита PostgreSQL отсутствует, поэтому серверная
   часть проверена чтением кода и тестами с подставными данными.
2. Браузеры Firefox и WebKit для кросс-браузерной проверки
   (`npx playwright install firefox webkit`).
3. Решение по R-01 и R-02 — это продуктовые вопросы, а не технические.
