# Чек-лист перед публикацией обновления

## 1. Перед сборкой
- [ ] `npm run verify` — зелёный (линтер, типы, 66 тестов, сборка)
- [ ] `npm run test:e2e` — 63/63
- [ ] `npm run test:db` — 20/20 (нужна поднятая база; без неё тест сообщает, что пропущен)
- [ ] `git status` чист, изменения закоммичены в рабочую ветку
- [ ] В коммитах нет секретов, `.env` не добавлен в индекс

## 2. Резервная копия (обязательно)
- [ ] Сделан дамп базы: `docker compose exec postgres pg_dump -U ithona ithona > backup_$(date +%F).sql`
- [ ] Дамп скопирован **за пределы сервера**
- [ ] Проверено, что дамп не пустой (`ls -lh`)

## 3. Развёртывание
```bash
cd /opt/ithona/app
git pull origin <ветка>
docker compose up -d --build          # или только frontend, если менялся фронтенд
```
- [ ] Сборка прошла без ошибок
- [ ] `docker compose ps` — все сервисы `running`
- [ ] `docker compose logs api --tail=50` — нет ошибок, есть «схема БД готова»

## 4. Проверка после развёртывания
- [ ] Сайт открывается, вход работает
- [ ] Данные на месте: проекты, задачи, комментарии
- [ ] Создание и перемещение карточки сохраняются после перезагрузки
- [ ] `curl -s https://<домен>/api/health` — `"status":"ok"`
- [ ] Заголовки безопасности отдаются:
      `curl -sI https://<домен> | grep -i -E 'content-security|x-frame'`
- [ ] Telegram-уведомления приходят (если бот подключён)
- [ ] Проверка на телефоне: интерфейс не разъезжается

## 5. Если что-то пошло не так
```bash
git checkout <предыдущий коммит>
docker compose up -d --build
```
Восстановление данных — из дампа (пункт 2) либо из снимка `board_history`
(см. `TESTING_GUIDE.md`, раздел «Восстановление доски из снимка»).

## 6. Не публиковать, если
- [ ] есть незакрытые дефекты уровня P0
- [ ] не проходит production-сборка
- [ ] не сделана резервная копия базы
- [ ] тесты не запускались
