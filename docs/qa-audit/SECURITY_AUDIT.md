# Аудит безопасности

Проверка по минимальному набору OWASP. Разрушительные атаки и нагрузочное
тестирование боевого сервера не проводились. Секреты в отчёте не раскрываются.

## Подробности

### Секреты
Файлы `.env`, ключи и сертификаты в индексе git отсутствуют. `.gitignore`
исключает `.env` и `.env.*`, кроме `.env.example`, в котором только
заполнители (`change_me_strong_password`). Токен Telegram, пароли базы и
код-приглашение читаются из окружения. Утечек в логи не найдено: сервер
пишет только текст ошибок, без тел запросов и заголовков.

### Пароли и сессии
Хеширование — `scrypt` с 16-байтовой солью на пользователя, сравнение
через `timingSafeEqual`. Сессия — случайный 24-байтовый токен в таблице
`sessions`, cookie `HttpOnly`, `SameSite=Lax`, `Path=/`, срок 30 дней;
флаг `Secure` добавляется при работе по HTTPS (B-05). Смена пароля требует
текущий пароль. Сброс пароля администратором завершает все сессии сотрудника.

### Инъекции
Все обращения к PostgreSQL используют подстановку параметров (`$1`, `$2`).
Конкатенации пользовательского ввода в SQL нет. Единственная интерполяция —
константа срока жизни сессии, задаваемая в коде.

### XSS
В коде нет `dangerouslySetInnerHTML`, `eval` и записи `innerHTML`; React
экранирует вывод. Аватары принимаются только как `data:image/(png|jpeg|webp|gif)`
— формат `svg+xml`, допускающий выполнение скриптов, отклоняется.
E2E-проверка: `<img src=x onerror="window.__xss=1">` в названии задачи выводится
как текст, обработчик не срабатывает.

### Права доступа
Роль вычисляется на сервере при регистрации (первый пользователь — `admin`) и
через API не изменяется: эндпоинт профиля обновляет только имя, e-mail, отдел,
должность и дату рождения. Операции над собственными данными используют
идентификатор из сессии. Сброс чужого пароля доступен только роли `admin`.

**Ограничение, о котором нужно знать:** разграничения прав на содержимое доски
нет — любой вошедший сотрудник может изменить и удалить любой проект
(см. `BUGS_REMAINING.md`, R-02). Это не уязвимость обхода защиты, а
нереализованная ролевая модель.

### Многокомпанийность
Система однокомпанийная: одна доска на инсталляцию (`board_state.id='default'`).
Проверки «пользователь компании A не видит данные компании B» неприменимы —
разделения на компании в коде нет.

### Заголовки (после исправления B-06)
`Content-Security-Policy` (скрипты только со своего домена, `frame-ancestors 'none'`,
`object-src 'none'`, шрифты Google, `data:`-картинки для аватаров),
`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`,
скрытие заголовка `Server`. Вступают в силу после перезапуска Caddy.

### Зависимости
Полноценный `npm audit` в среде аудита выполнить не удалось (нет доступа к
реестру npm). Состав зависимостей минимален и известен: React, Vite, Tailwind,
@dnd-kit, lucide-react, clsx, tailwind-merge; на сервере — `pg` и `ioredis`.
**Рекомендация:** выполнить `npm audit` и `npm audit --prefix api` на машине с
доступом в интернет и обновить пакеты с известными уязвимостями.

## Рекомендации по приоритету

1. Реализовать разграничение прав на операции с проектами (R-02).
2. Устранить потерю правок при одновременной работе (R-01) — сейчас это
   основной риск для целостности данных.
3. Регулярно выполнять `npm audit` и обновлять зависимости.
4. Настроить автоматические резервные копии базы (`deploy/backup.sh`) по
   расписанию и проверить восстановление на тестовом стенде.
