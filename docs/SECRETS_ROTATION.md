# Смена паролей и секретов

Инструкция на случай, когда содержимое `.env` могло попасть в чужие руки
(переписка, скриншот, общий экран). Все шаги выполняются на сервере в каталоге
`/opt/ithona/app`.

Порядок важен: пароль базы меняется **сначала внутри самой базы**, и только
потом в `.env`. Если поменять только в файле, API потеряет подключение.

---

## Шаг 0. Резервная копия (обязательно)

```bash
cd /opt/ithona/app
docker compose exec -T postgres pg_dump -U ithona ithona > ~/backup_$(date +%F_%H%M).sql
ls -lh ~/backup_*.sql
```

Файл должен быть **не пустым** (хотя бы десятки килобайт). Если он нулевого
размера — дальше не идите, разберитесь с дампом.

---

## Шаг 1. Сгенерируйте новые пароли

```bash
echo "POSTGRES:  $(openssl rand -hex 24)"
echo "MINIO:     $(openssl rand -hex 24)"
```

Используется `-hex`, а не `-base64`, намеренно: пароль базы подставляется в
адрес подключения `postgres://пользователь:пароль@postgres:5432/база`, и
символы `/`, `+`, `=`, `@` из base64 сломали бы разбор этого адреса.
Шестнадцатеричная строка состоит только из `0–9a–f` и безопасна и в адресе,
и в `.env`.

Скопируйте оба значения в надёжное место (менеджер паролей).

---

## Шаг 2. Смените пароль внутри базы

```bash
docker compose exec postgres psql -U ithona -d ithona \
  -c "ALTER USER ithona WITH PASSWORD 'НОВЫЙ_ПАРОЛЬ_POSTGRES';"
```

Ответ `ALTER ROLE` означает успех. После этой команды API временно не сможет
подключиться — так и должно быть, поправим на следующем шаге.

---

## Шаг 3. Обновите .env

```bash
nano .env
```

Приведите к такому виду:

```
POSTGRES_PASSWORD=НОВЫЙ_ПАРОЛЬ_POSTGRES     ← тот же, что в шаге 2
MINIO_ROOT_PASSWORD=НОВЫЙ_ПАРОЛЬ_MINIO
AUTH_PASSWORD=
INVITE_CODE=
```

Про две пустые строки:

- `AUTH_PASSWORD` — это пароль общего входа «один на всех». Он не используется,
  пока работают личные аккаунты, поэтому проще очистить, чем менять.
- `INVITE_CODE` — код-приглашение. Больше не нужен: регистрация идёт по коду из
  письма. Пустое значение его отключает.

Сохранить: `Ctrl+O`, `Enter`, выйти: `Ctrl+X`.

---

## Шаг 4. Примените

```bash
docker compose up -d
```

MinIO подхватит новый пароль при перезапуске, API — новый адрес подключения.

---

## Шаг 5. Проверьте, что всё поднялось

```bash
docker compose ps                       # все сервисы running
curl -s localhost/api/health            # ожидается "status":"ok"
docker compose logs api --tail=30       # без ошибок подключения к БД
```

В логах API должна быть строка `[api] схема БД готова`.

Затем откройте сайт:

- вход выполняется;
- проекты и задачи на месте;
- новая карточка сохраняется после перезагрузки страницы.

---

## Если API не подключается к базе

Признак: в логах `password authentication failed for user "ithona"`.
Значит пароль в базе и в `.env` разошлись. Повторите шаг 2 с тем значением,
которое стоит сейчас в `.env`, и перезапустите:

```bash
docker compose up -d api
```

Данные при этом не страдают: меняется только пароль пользователя.

---

## Восстановление из резервной копии (если понадобится)

```bash
cat ~/backup_ДАТА.sql | docker compose exec -T postgres psql -U ithona -d ithona
```

---

## Что ещё поменять вне сервера

- **Пароль приложения Zoho** (`SMTP_PASS`) — если он тоже мог попасть в чужие
  руки: `accounts.zoho.com` под `core@ithona.tj` → Security → App Passwords →
  удалить старый, создать новый, вписать в `.env`, `docker compose up -d api`.
- **Пароль ящика `core@ithona.tj`** — меняется в `mailadmin.zoho.com`.

---

## Как не повторить

- Не отправляйте `.env` и скриншоты с ним никому.
- Чтобы показать настройки, скрывайте значения:
  ```bash
  sed -E 's/=(.+)/=***/' .env
  ```
- Для проверки почты используйте `send-test-mail.js` — он не печатает пароль.
- После команд с паролем в строке очищайте историю: `history -c`.
