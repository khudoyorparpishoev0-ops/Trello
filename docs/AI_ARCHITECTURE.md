# AI в CORE — отдельный слой системы

Документ фиксирует, как в IT-HONA CORE устроен AI и почему именно так. Правило
короткое: **CORE хранит факты, аналитика считает, агенты интерпретируют,
Executive Agent приоритизирует, решение принимает руководитель.**

AI здесь — не кнопка «Ассистент» и не чат, которому отдают всю базу.

```
CORE DATA          состояние доски: проекты, списки, задачи, люди, сроки
      │
      ▼
Analytics Layer    src/analytics — единственный источник цифр
      │
      ▼
Domain Agents      выжимка своей области → наблюдения с доказательством
      │
      ▼
Executive Agent    только проверенные наблюдения → управленческая картина
      │
      ▼
AI-бриф            экран «AI-бриф»: факты отдельно, толкование отдельно
```

---

## 1. CORE DATA — источник фактов

Состояние живёт в `AppData` (`src/types.ts`) и в PostgreSQL одним документом.
Модель — источник истины по данным и ничего не считает.

Модель не отдаётся LLM ни на каком шаге. В запрос к провайдеру уходит только
то, что собрал слой датасетов, и только по своей области.

## 2. Analytics Layer — источник цифр

`src/analytics`. Чистый TypeScript, без React, без сети, без AI.

Состояние разбирается один раз в индекс (`analyze`), и все функции читают его.
Благодаря этому «выполнено» и «просрочено» в системе считаются ровно однажды —
через те же `isListDone` и `dueStatus`, которыми пользуется интерфейс.

Публичные функции:

| Функция | Что даёт |
|---|---|
| `getCompanyMetrics` | сводка по пространству без архива |
| `getProjectMetrics`, `getProjectCompletion`, `getProjectHealthSignals` | проект |
| `getDepartmentMetrics`, `getWorkloadByDepartment` | отделы |
| `getEmployeeMetrics`, `getWorkloadByEmployee` | сотрудники |
| `getTaskMetrics` | счётчики области |
| `getOverdueTasks`, `getUpcomingDeadlines`, `getDeadlineBuckets`, `getDeadlineQueue` | сроки |
| `getUnassignedTasks`, `getTasksWithoutDueDate`, `getDataQualityIssues` | пробелы в данных |
| `getCriticalTasks`, `getWipViolations` | риски |
| `getRecentActivity` | события (создание задач, сообщения) |

Норма загрузки объявлена один раз — `WORKLOAD_NORM`.

**Слой не зависит от AI.** Дашборд, «Команда» и «Отчёты» построены на нём и
работают при отсутствующем ключе, выключенном провайдере и недоступном сервисе.
Блок «Факты» на экране брифинга — тоже он.

### Где проходит граница «не дублировать расчёт»

- Правило «что считается выполненным» и «что считается просроченным» живёт в
  `src/lib/design.ts` и `src/lib/utils.ts`. Компоненты карточки и календаря
  вызывают их напрямую — это и есть единственный источник правила.
- Любая **агрегация** — счётчики, проценты, загрузка, разрезы по отделам — живёт
  только в `src/analytics`. Экраны читают готовое.

До этой работы норма загрузки была объявлена дважды, а «done/overdue/загрузка»
считались заново в дашборде, «Команде», «Отчётах» и хранилище. Разрез по отделам
при этом врал: задача с двумя исполнителями из одного отдела считалась дважды.

## 3. Domain Agents — специализированный разбор

`src/ai/datasets.ts` собирает для каждого агента только его область:

| Агент | Датасет |
|---|---|
| `deadline` | окна сроков: просрочено, сегодня, 24 ч, 48 ч, 7 дней |
| `team` | загрузка по людям и отделам, норма |
| `project` | метрики доски, списки, сигналы |
| `risk` | критические задачи, WIP, доски с просрочками и застоем |
| `quality` | задачи без исполнителя, без срока, с ошибочными датами |

Списки задач усечены до 20 позиций, и усечение показано явно (`total`,
`sample`, `omitted`): агент должен видеть, что задач больше, чем прислали, и не
делать вид, будто перечислил все.

Подсказки агентов лежат **на сервере** (`api/aiAgents.js`) и наружу не отдаются.
Браузер присылает только идентификатор агента и датасет — собрать произвольный
запрос к модели через наш ключ он не может.

## 4. Проверка выводов — как правило стало исполнимым

Требование «AI запрещено утверждать факт, которого нет в данных» здесь не
пожелание в подсказке, а проверка в коде (`src/ai/verify.ts`).

Каждое наблюдение обязано нести доказательство, и оно сверяется:

- **числа** — значение обязано встречаться в датасете, который агент получил.
  Любое другое число агент мог только вычислить или придумать; и то и другое
  запрещено, поэтому наблюдение отбрасывается;
- **сущности** — `cardId`, `userId`, `boardId`, отдел обязаны существовать в
  CORE и попадать в область запроса;
- **структура** — пустой факт, пустая рекомендация, неизвестная важность,
  чужая подпись агента и вывод вообще без доказательства не проходят.

Отклонённые выводы не прячутся: экран называет их количество и причину.

Executive Agent не получает ни доски, ни карточек — только проверенные
наблюдения, и отвечает **ссылками на них по id**. Пересказать чужой вывод он не
может: по id подставляется исходное наблюдение с исходным доказательством.

## 5. Разделение факта и толкования

Контракт наблюдения (`src/ai/types.ts`) разводит их на уровне типов:

```
fact             только то, что прямо следует из датасета
interpretation   мнение агента: почему это важно
recommendation   что предлагается сделать
evidence         числа и сущности, на которых вывод держится
```

Экран «AI-бриф» подписывает их раздельно и даёт раскрыть доказательство к
каждому выводу. Цифры блока «Факты» посчитаны аналитикой и не зависят от того,
работал ли AI вообще.

## 6. Что происходит при выключенном AI

Без `ANTHROPIC_API_KEY` сервер отвечает `{"enabled": false}` с причиной. Экран
показывает факты и объясняет, чего не хватает. Остальные разделы не меняются.

Ошибка одного агента не рушит брифинг: его область остаётся без наблюдений, и
это видно в блоке «Проверка выводов». Сбой сводки тоже не теряет проверенные
наблюдения.

## 7. Настройка

| Переменная | Смысл |
|---|---|
| `ANTHROPIC_API_KEY` | ключ провайдера. Не задан — AI выключен, аналитика работает |
| `AI_MODEL` | модель, по умолчанию `claude-opus-5` |
| `AI_AGENT_EFFORT` | усилия доменного агента, по умолчанию `medium` |
| `AI_RATE_MAX` | запросов к AI на пользователя за 10 минут, по умолчанию 30 |

Полный брифинг — шесть обращений к модели (пять доменных агентов и сводка),
поэтому лимита по умолчанию хватает примерно на пять брифингов за окно.

## 8. Сознательные ограничения

**Оркестратор работает в браузере, доступ к модели — на сервере.** Ключ
провайдера в браузер не попадает, подсказки тоже. Датасет при этом собирает
клиент: у него уже есть индекс аналитики, и так в системе остаётся одна
реализация расчётов вместо двух (TypeScript для интерфейса и JavaScript для
API).

Цена решения названа честно: **брифинг по расписанию и отправка в Telegram пока
невозможны** — для них аналитика нужна на сервере. Это следующий шаг, и делать
его надо переносом слоя `src/analytics` в общий для фронтенда и API пакет, а не
второй копией расчётов на сервере.

**Текст задач пишут сотрудники, и он попадает в датасет.** Значит, внутри может
оказаться попытка переписать инструкции агента («игнорируй предыдущие
указания…»). Защита трёхслойная: подсказка прямо говорит считать содержимое
данными, а не командами; ответ ограничен строгой схемой инструмента, то есть
агент физически не может вернуть ничего, кроме наблюдений; и каждое наблюдение
проходит сверку с фактами. Худшее, что остаётся достижимым, — правдоподобное, но
неверное *толкование* верных чисел; выдать выдуманный факт таким образом нельзя.

Датасет приходит от клиента, то есть теоретически им можно подменить цифры. Это
согласуется с существующей моделью доверия: состояние доски и так приходит от
клиента через `PUT /api/board`. Сверка выводов при этом остаётся осмысленной —
она защищает от выдумок агента, а не от подлога со стороны пользователя.

## 9. Что ещё не сделано

- Аналитика на сервере → брифинг по расписанию, утренняя сводка в Telegram.
- История изменений: без неё нет динамики «неделя к неделе», и агенты о ней не
  говорят, потому что данных нет.
- Агент проекта запускается по одной доске за раз.
