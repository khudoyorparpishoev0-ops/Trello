# Журнал доменных событий CORE

Документ описывает, как CORE записывает историю работы: что считается
событием, откуда оно берётся, чем защищено от дублей и чего в нём намеренно
нет.

---

## 1. Одно сравнение состояний на систему

Доска сохраняется целиком одним документом, поэтому «что изменилось» нужно
выводить сравнением прежнего и нового состояния. До этой фазы такое сравнение
делалось дважды: отдельно для уведомлений о назначении и отдельно для
уведомлений о смене срока. Журнал стал бы третьим — и в системе появилось бы
три ответа на один вопрос.

Теперь сравнение одно:

```
prevData + nextData
        ↓
  diffBoardState()          shared/domain/diff.ts
        ↓
   BoardChangeSet
      ↙        ↘
уведомления   журнал событий
```

`diffBoardState` — чистая функция: ни базы, ни сети, ни времени. Она лежит в
общем коде, значит доступна и серверу, и (при необходимости) интерфейсу.

Уведомления Telegram больше ничего не сравнивают сами — они принимают готовый
набор изменений. Поведение для сотрудников при этом не изменилось: те же
адресаты, те же поводы, автор изменения по-прежнему не получает уведомления о
собственном действии.

## 2. Набор изменений

`BoardChangeSet` (`shared/domain/diff.ts`) — плоская типизированная структура.
Новый вид изменения добавляется новым полем, старые потребители не ломаются.

| Поле | Когда заполняется |
|---|---|
| `taskCreated` | карточки не было в прежнем состоянии |
| `taskMoved` | карточка сменила список |
| `taskCompleted` | карточка попала в список со статусом «выполнено» |
| `taskReopened` | карточка вышла из такого списка |
| `assigneeAdded` / `assigneeRemoved` | изменился состав исполнителей |
| `dueChanged` | изменился срок (пустая строка и отсутствие — одно и то же) |
| `priorityChanged` | изменился приоритет |
| `commentCreated` | у карточки появился комментарий с новым `id` |
| `projectCreated` / `projectArchived` / `projectRestored` | изменения проекта |

## 3. Что событием не считается

**Общего «задача изменена» нет.** Правка заголовка или описания в журнал не
попадает. Такое событие срабатывало бы на каждое техническое сохранение и за
неделю превратило бы историю в шум, из которого нельзя посчитать ни время
закрытия задачи, ни движение проекта.

**У новой карточки не бывает «перемещения» и «смены срока».** Создание — один
факт, а не три. Иначе одно действие пользователя давало бы три записи, и
среднее время работы над задачей считалось бы по несуществующим переходам.

**Но назначение на новой карточке событием считается.** Это отдельный факт, и
именно на нём держатся уведомления о назначении, работавшие до журнала.

**Пометка списка «выполнено» закрывает все его задачи.** Действие одно, фактов
столько, сколько задач — и это правда: закрылась каждая из них.

## 4. Типы событий и их содержимое

Нагрузка минимальна: только то, что нельзя восстановить по ссылкам. Карточка
целиком в событие не копируется — для этого есть сама доска.

| `event_type` | `payload` |
|---|---|
| `task.created` | `{ listId, title }` |
| `task.moved` | `{ fromListId, toListId }` |
| `task.completed` · `task.reopened` | `{ listId }` |
| `task.assignee_added` · `task.assignee_removed` | `{ userId }` |
| `task.due_changed` | `{ from, to }` |
| `task.priority_changed` | `{ from, to }` |
| `comment.created` | `{ commentId, authorId, createdAt }` |
| `project.created` · `project.archived` · `project.restored` | `{ name }` |

`project.deleted` не заводится: удаление проекта доступно только
администратору и уже защищено на сервере, а снимок прежнего состояния уходит в
`board_history`. Вводить событие ради него без отдельного разбора этой защиты
рано.

## 5. Кто автор

`actor_user_id` — тот, чьим запросом сохранена доска. Системное изменение
оставляет поле пустым. **Автор не угадывается по исполнителю.**

`subject_user_id` — о ком событие: назначенный исполнитель, автор
комментария. Это разные вещи, и они разведены намеренно.

## 6. Схема

```sql
CREATE TABLE core_events (
  id              bigserial PRIMARY KEY,
  workspace_id    text NOT NULL,
  board_id        text,
  card_id         text,
  subject_user_id text,
  actor_user_id   text,
  event_type      text NOT NULL,
  payload         jsonb NOT NULL DEFAULT '{}',
  board_version   bigint NOT NULL,
  event_key       text NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX core_events_key_idx ON core_events (event_key);
```

Плюс индексы под будущие выборки: по времени в пространстве, по проекту и типу,
по версии доски.

Таблица **append-only**: ни `UPDATE`, ни `DELETE` над ней в коде нет.

## 7. Защита от дублей

Ключ события детерминирован:

```
workspace | vВЕРСИЯ | тип | сущность | отпечаток нагрузки
```

Отпечаток считается по JSON с упорядоченными ключами, поэтому перестановка
полей ключ не меняет. Два однотипных события одной карточки в одной версии —
например, назначение двух разных людей — получают разные ключи.

Вставка идёт с `ON CONFLICT (event_key) DO NOTHING`. Повторная обработка одной
версии доски не создаёт второй записи, и это свойство базы, а не памяти
процесса: перезапуск API ничего не ломает.

Дублей не возникает и по построению: версия доски растёт на каждой записи, а
повторная отправка того же состояния даёт пустой набор изменений.

## 8. Граница транзакции

```
BEGIN
  SELECT … FOR UPDATE          блокировка строки доски
  проверка версии              не сошлась → ROLLBACK, 409
  SAVEPOINT снимок истории     его сбой не стоит сохранения доски
  UPDATE board_state
  INSERT core_events …ON CONFLICT DO NOTHING
COMMIT
        ↓
уведомления Telegram           уже после фиксации
```

Невозможны оба плохих исхода: доска сохранена без событий или события записаны
без доски.

Уведомления отправляются **после** фиксации и намеренно не влияют на неё:
недоступный Telegram не должен стоить компании сохранённой работы. Ошибка
отправки пишется в лог.

Отказы не оставляют следа: ни конфликт версий (409), ни запрет на удаление
проекта (403) событий не создают — до записи дело не доходит.

## 9. Граница пространства

Доступ к доске и журналу идёт через репозиторий (`api/boardRepo.js`), все
методы которого принимают `workspaceId` первым параметром. Пространство пока
одно, его идентификатор объявлен один раз в
`shared/domain/workspace.ts`. Запись события с чужим `workspaceId` отвергается.

## 10. Ограничение истории

**Историческая аналитика доступна с даты включения журнала событий.**

Прошлое не реконструируется. В `board_history` лежат снимки доски, а не
события; выводить из них, что происходило между снимками, — это домыслы, а не
факты. Показатели «неделя к неделе» не показываются, пока не накопится
достаточный период.
